# @mbtech-nl/bitmap — Documentation Site Plan

> Build a VitePress documentation site published to GitHub Pages at
> `https://mbtech-nl.github.io/bitmap/`, plus a slimmed README.md that
> remains friendly on npm and the GitHub repo landing page.
>
> Scope:
> - Visual gallery for all dither methods on multiple source images
> - Tone control demos (`autoLevels`, `gamma`, `luminanceWeights`)
> - Multi-plane walkthrough with classification + per-plane render images
> - Pipeline-order diagram
> - Recipes / cookbook
> - Generated API reference (TypeDoc) for every export from [src/index.ts](src/index.ts)
> - Interactive in-browser **playground** — drop an image, tweak options, see live output
>
> Out of scope: versioned docs (`/v1/`, `/v2/`), i18n, custom domain.

---

## 0. Decisions made (locked)

| Decision | Choice | Rationale |
| --- | --- | --- |
| Approach | VitePress on GitHub Pages | Visual gallery is the load-bearing piece; reads materially better as a real page than as a 21-image block in one README. |
| Hosting URL | `https://mbtech-nl.github.io/bitmap/` | Repo-default. Sets `base: '/bitmap/'` in VitePress config. |
| Fixture images | Source from CC0 sets (Unsplash/Pexels/Wikimedia public domain) **and** generate procedural fixtures (gradients, geometric line-art, synthetic colour-test charts) where useful. All committed to `docs/fixtures/` with a `CREDITS.md` listing source + license per file. | We control redistribution and can regenerate procedurally on demand. |
| Playground | **In scope for v1 docs.** Drop-image + live-render Vue component embedded in the dither / tone / multi-plane pages. Bitmap lib is zero-dep and DOM-free, so it runs unchanged in the browser. | High-value evaluation tool; cost is bounded because the lib already runs in browsers. |
| Versioning | Single "docs reflect main" site for now. | Lib is pre-2.0, churn is low; revisit if we cut a v2. |

Any deviation from the table above is a design change and must be logged in the decision log (§ 11) before the implementing PR lands.

```json
{
  "docs:images": "node --experimental-strip-types scripts/build-docs-images.ts",
  "docs:api": "typedoc",
  "docs:dev": "pnpm docs:api && vitepress dev docs",

```

Use Node 24's native `--experimental-strip-types` rather than adding `tsx` — engines already require Node ≥ 24.

## 3. Implementation phases

Each phase is intended to land as **one PR**. Phases are mostly independent, but the order below is the cheapest path through. Every phase ends with the quality gate from § 9.

### Phase 1 — Scaffold + deploy pipeline (foundation)

**Goal:** an empty VitePress site is reachable at the public URL.

- Add devDeps (vitepress, vue) via `pnpm add -D`.
- Create `docs/.vitepress/config.ts` with:
  - `base: '/bitmap/'`
  - `title: '@mbtech-nl/bitmap'`
  - empty sidebar/nav placeholders
- Create `docs/index.md` with a one-line "docs in progress" placeholder.
- Add `.github/workflows/deploy-docs.yml` using `actions/configure-pages` + `actions/upload-pages-artifact` + `actions/deploy-pages`. Triggers: `push` to `main` and `workflow_dispatch`. Uses `pnpm docs:build`.
- Enable Pages in repo settings (manual step — flag in PR description for the human reviewer).
- Add `docs/.vitepress/dist/` and `docs/api/` to [.gitignore](.gitignore) — but keep `docs/public/images/` tracked.

**Verify:** push branch, manually trigger workflow on a fork or via `workflow_dispatch` after merge; site renders at the URL.

### Phase 2 — TypeDoc API reference

**Goal:** generated API pages browsable in the local dev server.

- Add `typedoc` + `typedoc-plugin-markdown` devDeps.
- Create `typedoc.json` at repo root: entry `src/index.ts`, output `docs/api/`, plugin `typedoc-plugin-markdown`, `readme: 'none'`, `githubPages: false`.
- Sweep [src/index.ts](src/index.ts) and the modules it re-exports from ([src/image.ts](src/image.ts), [src/multiplane.ts](src/multiplane.ts), [src/dither.ts](src/dither.ts), [src/transform.ts](src/transform.ts), [src/encode.ts](src/encode.ts), [src/font/render.ts](src/font/render.ts), [src/types.ts](src/types.ts)) — every public export needs a TSDoc block with `@param`, `@returns`, `@throws` (where applicable), and `@example`. Existing docstrings stay; add what's missing. Do **not** rewrite working prose.
- Wire `docs:api` script. Wire VitePress sidebar to include the generated `api/` tree (either via `vitepress-plugin-typedoc` or by reading the generated `typedoc-sidebar.json` in `config.ts`).

**Verify:** `pnpm docs:dev` shows every export from `src/index.ts` under an "API" sidebar section with full signatures + examples.

### Phase 3 — Image generation pipeline

**Goal:** `pnpm docs:images` regenerates every gallery PNG deterministically from committed fixtures.

- Source 4–6 fixture images into `docs/fixtures/`:
  - `photo-portrait.jpg` — a portrait or scene with smooth gradients (Unsplash CC0, prefer one with a clear face / detail / smooth-sky region — exercises every dither method)
  - `photo-landscape.jpg` — second photo, different tonal character
  - `logo.png` — a clean two-tone logo (use the MBTech logo if available; otherwise generate a procedural one with `renderText` + filled rectangles)
  - `line-art.png` — generated procedurally: thin diagonals, concentric circles, fine text. Tests where dithering hurts.
  - `low-contrast-scan.jpg` — CC0 vintage scan or generated by compressing a photo's tonal range to [80, 160]. Drives the `autoLevels` demo.
  - `multi-colour-design.png` — generated procedurally: red+black+blue regions on white, with anti-aliased edges. Drives the multi-plane demo.
- Write `docs/fixtures/CREDITS.md` listing source + license per file.
- Build `scripts/build-docs-images.ts`:
  - Decode fixture PNGs/JPGs to RGBA (use `pngjs` for PNG, allow JPG by converting to PNG fixtures up front so the script only handles PNG — keeps deps minimal)
  - Iterate config matrix (see § 4 for the matrix)
  - Render via the lib's actual exports (import from `../src/index.ts` so docs always reflect HEAD)
  - Encode 1bpp `LabelBitmap` back to RGBA PNG (1 → black, 0 → white) and write to `docs/public/images/<page>/<name>.png`
  - For multi-plane outputs, optionally render a "composite" PNG (each plane in its palette colour, on white) for the gallery
- Add CI step: `pnpm docs:check-images` (regenerates and fails on diff). Wire into the existing CI workflow, not the docs deploy workflow.

**Verify:** delete `docs/public/images/`, run `pnpm docs:images`, all images regenerate identically (commit hash unchanged); CI guard catches a deliberate output change.

### Phase 4 — Dither gallery page

**Goal:** `docs/guide/dithering.md` shows side-by-side comparisons + decision matrix.

- Build the `DitherGallery.vue` component: responsive flexbox/CSS-grid of labelled image tiles. Accepts a list of `{ label, src }` and an optional column count.
- Write the page: one gallery per source image (logo, line-art, photo-portrait, photo-landscape) × all 7 modes (`false`, `floyd-steinberg`, `atkinson`, `stucki`, `jarvis-judice-ninke`, `bayer4`, `bayer8`).
- Port the "When to use what" table from [README.md](../../README.md) lines 47–56.
- Embed `<Playground />` at the bottom (component built in Phase 7; stub the import for now and uncomment when Phase 7 lands, or land Phase 7 first — see § 8).

### Phase 5 — Tone & luminance page

**Goal:** `docs/guide/tone-and-luminance.md` covers `autoLevels`, `gamma`, `luminanceWeights`.

- `autoLevels` before/after on the low-contrast fixture.
- `gamma` sweep: 0.6 / 0.8 / 1.0 / 1.2 / 1.5 on the same photo (single dither method, e.g. Floyd–Steinberg, so only gamma varies).
- `luminanceWeights`: `bt709` vs `bt601` vs `[1, 0, 0]` vs `[0, 1, 0]` on the multi-colour fixture.
- Embed `<Playground />` (same component as Phase 4) preconfigured to expose just these knobs.

### Phase 6 — Multi-plane page + pipeline diagram

**Goal:** `docs/guide/multi-plane.md` and `docs/guide/pipeline.md`.

- Multi-plane: port [README.md](../../README.md) lines 61–129 verbatim as the prose base, then add:
  - source-image preview
  - "classification map" PNG (each pixel coloured by which plane it landed in, white-substrate pixels stay white) — generated by the image script
  - per-plane PNGs (each rendered in its palette colour on white)
  - RGB vs Lab side-by-side on a 3-colour palette where the result actually differs
  - `<MultiPlanePlayground />` embed (Phase 7)
- Pipeline: render the `rgba → luminance → autoLevels → gamma → threshold|dither → rotate` chain as a diagram. **Mermaid `flowchart LR`** preferred — VitePress has built-in Mermaid support via `vitepress-plugin-mermaid`; no image asset to maintain. If that plugin is awkward, fall back to a hand-drawn SVG committed at `docs/public/images/pipeline.svg`. Log the choice in § 11.

### Phase 7 — Interactive playground

**Goal:** two Vue components embeddable in any page; live image-in / bitmap-out.

`Playground.vue` — single-plane:

- File input (drag-drop + click-to-select); read via `URL.createObjectURL` + `<img>` + `<canvas>` to extract `ImageData`.
- Optionally include 2–3 preset images (loaded from `/images/...`) so the page is interactive without requiring an upload.
- Controls (reactive `<select>`, `<input type="range">`, `<input type="number">`, `<input type="checkbox">`):
  - `dither` (dropdown of all 7 modes)
  - `threshold` (range 0–255, disabled when `dither !== false`)
  - `invert`
  - `rotate` (0/90/180/270)
  - `autoLevels`
  - `gamma` (range 0.2–3.0, step 0.05)
  - `luminanceWeights` (bt709/bt601/custom-tuple)
- Output: render result to a `<canvas>`, expand 1bpp → 8-bit greyscale ImageData (1 → 0, 0 → 255).
- Bonus: a "copy as code" button that emits the matching `renderImage(image, { ... })` snippet with the current options.

`MultiPlanePlayground.vue`:

- Same image-input mechanism.
- Palette editor: list of `{ name, rgb }` entries with add/remove/reorder; preset loaders for "Brother QL-800 red+black", "DYMO black+blue", "3-colour test".
- `colorSpace` toggle (rgb / lab).
- Per-plane `gamma` + `dither` overrides (collapsed by default).
- Output: one canvas per plane, plus a composite canvas overlaying all planes in their palette colours on white.

Implementation notes:

- Components live in `docs/.vitepress/theme/components/`, registered globally in `theme/index.ts` so any `.md` page can use them with `<Playground />`.
- Import the lib via `import { renderImage, renderMultiPlaneImage } from '../../../src'` — keeps docs site always-on-HEAD. Consider the `tsconfig` paths so the import resolves cleanly under VitePress's Vite config; document the resolution in § 11 if non-trivial.
- SSR-guard: VitePress builds pages statically. Wrap any `window`/`File`/`canvas` access in `<ClientOnly>` or check `import.meta.env.SSR`.
- Performance: re-render is cheap (single image, hundreds of µs), but debounce slider input by ~16ms to avoid jank on 4K displays.

### Phase 8 — Recipes

**Goal:** 4 short task-oriented snippets in `docs/recipes/`.

Start with the four listed in § 1; each is one page, ≤ 200 lines, focused on a runnable snippet + one explanatory paragraph. No need for fancy embeds.

### Phase 9 — Slim README.md + landing page polish

**Goal:** README.md and `docs/index.md` are both friendly entry points; no duplication beyond a teaser.

README.md keeps:
- Badges, install, the 5-line example
- The compact "When to use what" table (mirrored from `docs/guide/dithering.md`)
- Bit layout + browser support sections
- Prominent link: "Full documentation: https://mbtech-nl.github.io/bitmap/"
- License

README.md drops:
- Per-option tables (now generated in API ref)
- Multi-plane deep dive (lives at `/guide/multi-plane`)
- Pipeline-order section (lives at `/guide/pipeline`)
- API list (lives at `/api/`)

`docs/index.md` becomes the marketing page: hero, feature cards (one per major capability), "Get started" CTA, "Try it in the browser" CTA pointing into the playground.

4. `pnpm docs:build` → succeeds end-to-end
5. `pnpm docs:check-images` → no unexpected diff (only Phase 3 onward)

7. Update [progress.md](../progress.md) — see § 10
8. Update § 11 of this file with any decisions made — see § 11

### 2026-04-27 — Approach: VitePress over single-README

**Decision:** Build a VitePress site at `mbtech-nl.github.io/bitmap` rather than templating one README.md.
**Why:** The visual dither gallery is the load-bearing piece of the docs effort and reads materially better as a navigable site; the API surface is already 20+ exports.
**Affects:** entire docs effort.

### 2026-04-27 — Hosting URL: repo default

**Decision:** Use the GitHub-Pages default `https://mbtech-nl.github.io/bitmap/`. No custom domain.
**Why:** Zero DNS work; matches every other repo under the org. Revisit if the project grows a public brand.
**Affects:** `docs/.vitepress/config.ts` (`base: '/bitmap/'`), CI deploy workflow.

### 2026-04-27 — Fixture images: CC0 + procedurally generated

**Decision:** Source from CC0 image banks for photos; generate procedurally for line-art, low-contrast, and multi-colour fixtures. Track origins in `docs/fixtures/CREDITS.md`.
**Why:** No redistribution risk; procedural fixtures are reproducible and exercise edge cases (sharp edges, tight tonal ranges, three-way colour boundaries) that real photos don't reliably hit.
**Affects:** `docs/fixtures/`, `scripts/build-docs-images.ts`.

### 2026-04-27 — Playground: in scope for v1

**Decision:** Ship `Playground.vue` and `MultiPlanePlayground.vue` as part of the initial docs release.
**Why:** Lib is browser-clean (zero deps, no DOM APIs), so the marginal cost is bounded; live demos are unusually compelling for an image-processing library.
**Affects:** Phases 4, 5, 6, 7.

### 2026-04-27 — Use `node --experimental-strip-types` over tsx

**Decision:** Run `scripts/build-docs-images.ts` via Node's native TS stripping.
**Why:** Engines already require Node ≥ 24, and `tsx` is not transitively exposed by vitest. Native stripping is one less devDep.
**Affects:** [package.json](package.json) scripts, Phase 3.

### 2026-04-27 — Vite alias `@bitmap` → `src/`

**Decision:** Playground components import via `@bitmap`, not deep relative paths.
**Why:** Source uses `.js` import suffixes; deep relative paths from `docs/.vitepress/theme/components/` to `src/` resolve poorly under Vite's default config. A single alias is robust and readable.
**Affects:** `docs/.vitepress/config.ts`, Phase 7.

### 2026-04-27 — Patch bump assumes zero lib fixes

**Decision:** Docs effort ships under one patch bump (1.2.0 → 1.2.1). If the playground surfaces a real lib bug, that fix is its own patch shipped first, then the docs PR.
**Why:** Keeps version semantics honest — patch shouldn't bundle behaviour changes with documentation.
**Affects:** Phase 9, release process.

## 11.5 Known traps (folded in from gap review)

Read these before each phase touches the relevant area.

**PNG determinism for the CI diff guard (Phase 3).** `pngjs` writes a `tIME` chunk by default and zlib compression varies across libc/Node versions. The `git diff --exit-code` guard will throw cross-platform false positives unless we strip non-essential chunks and pin the deflate level. The image script must:
- pass `deflateLevel: 9, deflateStrategy: 3, filterType: 0` to `PNG` constructor
- never write `tIME` / `tEXt` / `iTXt` / `pHYs` chunks (pngjs default is acceptable but verify with `pngcheck` once during Phase 3)
- if drift still appears across CI vs dev, switch the guard to a pixel-data hash comparison instead of byte-level git diff.

**Vite alias for source imports (Phase 7).** Source files use `.js`-suffixed imports (e.g. `from './types.js'` in [src/index.ts](src/index.ts)). The naive `import { renderImage } from '../../../src'` from a Vue component is fragile. In `docs/.vitepress/config.ts`, add:
```ts
vite: {
  resolve: {
    alias: { '@bitmap': fileURLToPath(new URL('../../src', import.meta.url)) }
  }
}
```
and import as `from '@bitmap'` everywhere.

**First GitHub Pages deploy (Phase 1).** Pages source must be set to **"GitHub Actions"** in repo settings, not the default "Deploy from a branch". The first push to main *will* fail until that switch is flipped — this is normal. After flipping, re-run via `workflow_dispatch`.

**Pin Node 24 + pnpm 9 in CI (Phase 1).** [package.json](package.json) `engines` requires `node >=24` and `pnpm >=9`. Both deploy and main CI workflows must pin explicitly:
```yaml
- uses: actions/setup-node@v4
  with: { node-version: 24 }
- uses: pnpm/action-setup@v4
  with: { version: 9 }
```

**TypeDoc + plugin major-version match (Phase 2).** `typedoc-plugin-markdown@4` requires `typedoc@0.26+`. Pin compatible majors at install or `pnpm install` will warn and the generated output may be empty.

**Gallery image budget (Phase 3).** ~60 PNGs land in `docs/public/images/`. 1bpp content compresses extremely well, but cap output dimensions to **600×600 max** to keep repo size reasonable.

**README slimming is a user-visible npm change (Phase 9).** README is what npmjs.com renders. Slimming it is intentional but is a real product change shipped under the patch bump. Mention this in the Phase 9 PR description.

**Patch-bump assumes zero lib fixes.** § 7 says "fix the lib" if the playground exposes Node-only assumptions. If that happens, ship the lib fix as its own patch first, *then* the docs PR. Do not fold a lib fix into a docs PR — it muddies the version semantics.
